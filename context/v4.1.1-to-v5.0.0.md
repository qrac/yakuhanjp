# v4.1.1からv5.0.0への変更点

記録日：2026-10-21。v5.0.0は開発中です。

## 比較の基準

- 旧版：Gitタグ`4.1.1`（`bd6d223730b079717a6ffa9c9e8eb3d02df16222`）
- 新版：HEAD `ef2c6c86da51cdc4387500c966e2e5d562682570`と、作業ツリーの未コミット更新を合わせた状態
- 未コミット更新には、OTFの曲線変換・CFF命令の共通化と、再生成したOTFを含む

この資料は、このチャット内の変更だけでなく、タグ`4.1.1`以降のリポジトリ全体の変更を対象とします。
`v5.0.0`という表記は開発中のバージョンを指し、リリース済みという意味ではありません。

| 項目 | v4.1.1 | 開発中のv5.0.0 |
| --- | --- | --- |

## 維持している利用方法と仕様

[`packages/yakuhanjp/project.json`](../packages/yakuhanjp/project.json)は、タグ`4.1.1`と現在で同一です。
以下の情報は維持しています。

- 6ファミリー：`YakuHanJP`、`YakuHanJPs`、`YakuHanMP`、`YakuHanMPs`、`YakuHanRP`、`YakuHanRPs`
- スタイル数：JP/JPsは各9、MP/MPs/RP/RPsは各7、合計46
- 通常版とカッコ限定版の区分、宣言している収録文字、CSSのウェイト指定
- 元フォント：Noto Sans JP、Noto Serif JP、M PLUS Rounded 1c
- `resource`内の元フォントとライセンスファイル。比較対象期間に変更はない
- npmのパッケージ名`yakuhanjp`、メインのCSSパス、6つの配布CSS名、`dist/fonts/<family>/`の配置
- `font-display: swap`と、通常CSS・jsDelivr用CSSの提供
- パッケージのライセンス表記`(OFL-1.1 AND MIT)`

たとえば、次の読み込み方は維持しています。

```js
import "yakuhanjp"
import "yakuhanjp/dist/css/yakuhanjp_s.css"
import "yakuhanjp/dist/css/yakuhanmp.css"
```

CDNをバージョン固定で利用する場合は、v5公開後にURLのバージョンを変更する必要があります。
フォントのバイナリやマージ版の文字送りまで、旧版と完全に同じという意味ではありません。

## フォントの編集と生成

### Glyphs形式からJSONへ移行

`packages/core`にあった46個の`.glyphs`ファイルを削除し、次の2種類のJSONに移しました。

```text
packages/core/<family>/
├── sources/<Style>.json   # 文字、余白、固定幅、縦書き、メタデータ
└── outlines/<Style>.json  # 字形の輪郭
```

既存の字形と数値を移行しており、調整のためにGlyphsアプリを用意する必要はありません。
生成処理は[`scripts/font_sources.py`](../scripts/font_sources.py)、ビルド・マージ・形式変換とキャッシュは
[`scripts/build_fonts.py`](../scripts/build_fonts.py)が担当します。
Glyphs形式の読み込み用ライブラリも通常の依存から外しています。

### 幅・余白・文字追加の指定

編集元は`packages/core/<family>/sources/<Style>.json`です。
主な設定は次のとおりです。

- `characters`：その字形を割り当てる文字
- `left`、`right`：左右の余白。送り幅は「左余白＋輪郭の境界幅＋右余白」から計算
- `advanceWidth`：任意の固定送り幅。指定すると右余白からの幅計算より優先
- `offsetY`：輪郭の上下移動
- `advanceHeight`、`verticalOrigin`、`verticalGlyph`：縦書きの送り・原点・代替字形
- `source.character`：保存済み輪郭の代わりに、元フォントから指定文字の輪郭を取り出す
- `metadata`：名前、ウェイト、ライセンス、行の高さなど

たとえばYakuHanJP Regularの`「`は、左余白200、右余白34です。
数値は1000が1emのフォント内部単位です。ウェイトごとに独立して編集できます。
収録文字を追加するときは、対象スタイルのJSONと`project.json`の`glyphs`を更新します。
具体例は[coreの編集ガイド](../packages/core/README.md)を参照してください。

### マージ版の作り方と挙動の差

元フォントの収録文字・OpenType機能を引き継ぎ、約物と縦書き用の代替字形を置き換えます。
半角化した字形には、`palt`・`halt`・`vpal`・`vhal`による追加の詰め処理を適用しません。
これにより、約物が二重に詰められることを防ぎます。

旧マージ版は、約物単体版と整形後の文字送りが異なるケースがあります。
たとえばYakuHanJP Regularの`！`をHarfBuzzの標準設定で横書き整形すると、旧マージ版の送りが500、新版が428です。
この数値は整形後の結果で、字形単体の`hmtx`の幅だけを比較した値ではありません。
新版は約物ソースの設定を採用するため、既存のマージ版を置き換える用途ではレイアウト確認が必要です。
約物単体のcoreでは、全46スタイルの横書き・縦書きの文字送りを既存出力と比較しています。

移行時に残っていた元フォント名・別スタイル名、OS/2のウェイトとフラグも、旧出力の情報に合わせて補正しました。
この移行では、OS/2の値とCSSのウェイトを新たに同一化していません。
たとえば旧出力でThin/ExtraLightがOS/2上250になっている設定は維持しています。

### ファイル容量の差

生成ツールと輪郭の格納方法が異なるため、同じ字形数でもバイナリの完全一致は目標にしていません。
以下はタグ`4.1.1`と、この資料作成時の`packages/core`のRegularの実測値です（単位：B）。

| ファミリー | 形式 | v4.1.1 | 現在 | 増減 |
| --- | --- | ---: | ---: | ---: |
| YakuHanJP | OTF | 6,036 | 5,536 | -500 |
| YakuHanJP | TTF | 7,076 | 6,660 | -416 |
| YakuHanJP | WOFF2 | 3,708 | 3,200 | -508 |
| YakuHanMP | OTF | 6,860 | 6,072 | -788 |
| YakuHanMP | TTF | 7,564 | 7,268 | -296 |
| YakuHanMP | WOFF2 | 4,204 | 3,464 | -740 |
| YakuHanRP | OTF | 6,392 | 6,388 | -4 |
| YakuHanRP | TTF | 7,588 | 7,316 | -272 |
| YakuHanRP | WOFF2 | 4,188 | 3,012 | -1,176 |

最適化前のOTFはJPが7,084 B、MPが7,640 B、RPが8,700 Bで、旧版より増えていました。
これは主にCFFの輪郭の格納方法によるもので、繰り返すCFF命令の共通化を行っていませんでした。
たとえば最適化前のYakuHanJP RegularではCFFが旧版の2,864 Bから4,293 Bへ増える一方、
`name`テーブルは1,753 Bから1,466 Bへ減っており、約1KBの増加はメタデータの増加ではありませんでした。
WOFF2も旧版のCFFベースからTTFベースへ変わっています。

現在は、TTFからOTFへの変換で次の最適化を行います。

- 二次曲線を三次曲線へまとめ直し、CFFで記述する曲線数を削減。近似の許容誤差は1/1000emで、座標の丸めも行う
- `cffsubr`（AFDKOの`tx`）で繰り返すCFF命令をサブルーチンとして共通化。この処理自体は輪郭を変更しない
- 縦書き原点を`VORG`へ保存し、曲線変換後も文字の配置を維持

元フォントがCFFのMP/MPsのマージ版は、そのCFF構造を維持します。
JP/JPsとRP/RPsの元フォントはTTFなので、元のCFFをそのまま使う方法は取れません。
今回の最適化でTTF・Web用WOFF2の生成方法や輪郭は変更していません。

マージ版の実測値は次のとおりです（MBは1,000,000 B）。

| 対象 | 最適化前 | 最適化後 | 削減率 |
| --- | ---: | ---: | ---: |
| JPのOTF 9ファイル | 64,806,512 B | 35,380,708 B | 45.41% |
| JPsのOTF 9ファイル | 64,802,348 B | 35,379,872 B | 45.40% |
| MP/MPsのOTF 14ファイル | 86,449,196 B | 86,449,196 B | 変更なし |
| RPのOTF 7ファイル | 31,748,908 B | 14,143,560 B | 55.45% |
| RPsのOTF 7ファイル | 31,749,052 B | 14,140,096 B | 55.46% |
| OTF全46ファイル | 279,556,016 B | 185,493,432 B | 33.65% |
| TTFを含む全92ファイル | 535,355,048 B | 441,292,464 B | 17.57% |

最適化後のOTF合計は、v4.1.1の186,539,424 Bより0.56%小さくなりました。
v4.1.1と共通するTTF・OTFの64ファイルでは285,286,680 Bから288,639,428 Bへ、1.18%の増加です。
全92ファイルの合計が旧版より大きい主因は、MP/MPs/RP/RPsのTTF 28ファイル（152,653,036 B）を追加したことです。
最適化前後でTTF・WOFF2の全138ファイルと、MP/MPsのマージ版OTF全14ファイルのバイナリ一致を確認しました。

## ビルドと公開の変更

### ルートの一括ビルド

v4.1.1のルート`npm run build`は、`yakuhanjp`のCSS・配布ファイル生成だけを行っていました。
現在は次の順番です。

```text
npm run build
  ├─ build:fonts:packages
  │    └─ build:fonts -- --merged-format both --output packages
  │         ├─ build/fontsで生成・キャッシュ検証
  │         └─ packages/core・packages/mergedへ必要なファイルをコピー
  ├─ build:unicode
  │    └─ packages/unicode/dist/data.jsonを更新
  └─ build:main
       └─ packages/yakuhanjp/distを削除してCSS・WOFF2を生成
```

coreはTTF・OTF・WOFF2、mergedはTTF・OTFの両方を更新します。
途中の処理が失敗すると、後続の処理を実行しません。
`packages/yakuhanjp/package.json`の`prepublishOnly`も、`npm --prefix ../.. run build`で同じ処理を呼びます。
公開前フックの失敗はnpmによる公開を停止させます。

### 出力先とキャッシュ

| コマンド | 更新範囲 |
| --- | --- |
| `npm run build:fonts` | `build/fonts`にcoreの全形式と、mergedの元フォントと同じ形式を生成 |
| `npm run build:fonts -- --merged-format both` | `build/fonts`にmergedの両形式も生成 |
| `npm run build:fonts -- --merged-format both --output packages` | 生成・検証済みの全形式を`packages/core`・`packages/merged`へ反映 |
| `npm run build` | フォントの反映、Unicode、配布用CSS・WOFF2まで更新 |
| `npm run build:main` | 配布用CSS・WOFF2のみ更新。フォントの再生成は行わない |

生成とキャッシュは、出力先の指定にかかわらず`build/fonts`に集約します。
入力のJSON・輪郭・必要な元フォント・生成スクリプト・`uv.lock`と、出力ファイルのハッシュを検証します。
形式ごとに管理するため、元形式のみのビルドから`both`へ切り替えた場合は不足する形式だけを生成します。
出力先を変えても、同じ入力・形式ならコピーだけで済みます。コピー先の内容が同じ場合はコピーも省略します。
`--output packages`で編集元の`sources`や`outlines`を上書きすることはありません。

未変更の全グリフを保存時に再計算する処理も省略し、置き換える字形の境界・メトリクスを更新しています。
core/merged内の任意の古いファイルを一括削除する処理はありません。
一方、Unicodeと配布用の`dist`は作り直し、配布対象は`project.json`に記載したファミリーとスタイルに限定します。

### CSSとUnicodeの生成処理

- 手書きCSS6ファイルと、配布ビルド用のVite設定・CDN置換プラグインを削除
- `packages/yakuhanjp/src/generate.ts`で、`project.json`から`@font-face`、`unicode-range`、ライセンスバナー、通常版・CDN版CSSを生成
- フォントは`packages/core`のWOFF2を直接コピーし、ソースCSS内の参照を経由しない構成へ変更
- Unicode生成は`charCodeAt`・文字列の`split("")`から、`codePointAt`・コードポイント単位の列挙へ変更
- 補助文字（例：`𠮷`）を正しく扱い、数値順に並べ、空の1文字入力は`RangeError`にする
- `fs-extra`・`rimraf`による処理をNode標準のファイルAPIへ置き換え
- Unicode生成のJSON読み込みを、現在のNodeで扱えるデフォルトインポートへ修正

### 削除・置き換えした開発コマンド

| v4.1.1のコマンド | 現在の扱い |
| --- | --- |
| `build:src`、`build:main-src` | `build:main`で配布ファイルを生成。全体の更新は`build` |
| `build:unicode-src` | `build:unicode`へ集約 |
| `clean`、`clean:main` | 廃止。各dist生成処理で出力先を削除する |
| `play:ogp` | 廃止。`play:canvas`を使用する |

開発コードで`yakuhanjp/src/*.css`を直接参照していた部分は、`dist/css`の参照へ変更しています。
`npm run play`はルートの`build`を実行してから起動します。

## サイトとPlayground

### ドキュメントサイト

- minista 3から5へ更新し、設定を`docs/minista.config.ts`から`docs/vite.config.ts`へ移行
- 旧Preact設定を外し、`@tanstack/redact`のnanoプリセットとhydration設定を使用
- サイト情報・表示設定を`docs/project.json`へまとめ、レイアウト・共通部品・ページ部品を整理
- シミュレーターの文言・選択肢・表示設定をデータとpropsへ分離
- `contentEditable`での改行・空行、IME入力やキャレットを維持する処理を改善
- 操作グループ、編集欄の説明、選択状態などのアクセシビリティ情報を追加
- Google Fontsは選択に応じて読み込み、同じスタイルシートを重複追加しないよう変更
- コード例のハイライトはShikiでビルド時に生成。MDXにはrehype-pretty-codeを使用

### Playgroundと画像生成

- `_default`と`canvas`で選択肢・URL同期・スタイルを共通化
- URLのクエリから初期値と空文字を復元し、編集時は`replaceState`で履歴を増やさず更新
- フォントごとに実在するウェイトだけを画像生成用の選択肢として提示
- Canvas APIでHTTPメソッド・フォント名・ウェイトを検証し、無効な入力に400/405を返す
- フォントのパスをモジュール位置基準で解決し、TTF/OTFの両方を受け付ける
- フォント登録を再利用し、改行を正規化して1200×630のPNGを生成
- Satori・resvgを使う`playground/ogp`を削除し、OGPの例を`node-canvas`へ集約

これらは開発用の画面・APIです。npmパッケージに画像生成サーバーを同梱する変更ではありません。
