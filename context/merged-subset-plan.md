更新日：2026-10-21。状態：初期調査と計画。文字セット・命名・配布仕様は未確定、生成処理は未実装。

## 依頼で示された前提

- `merged/full`と`merged/subset`で分ける想定。
- ゲーム・アプリへの内包を主用途とする。
- サブセットのWebフォント版（WOFF/WOFF2・CSS・unicode-range分割）は作らない。
- 第一水準・第二水準だけで分けず、現代日本語での使用頻度を反映した文字セットを検討する。
- ファイル名のどこに`subset`を入れるかは未定。
- [ixkaito/NotoSansJP-subset](https://github.com/ixkaito/NotoSansJP-subset/blob/master/README.md)は参考例。互換や踏襲は要件ではない。

## 現時点の推奨案（提案）

「共通の基礎文字＋複数資料の頻出漢字＋用途上必要な追加文字」で、包含関係のある候補を比較する。
公開する段階数は容量・欠字の実測後に決める。最初から多数のバリエーションを配布しない。

汎用プリセットだけでは固有名詞や作品独自の語彙を保証できないため、将来の作品テキスト追加・欠字検査にも使える
機械可読の文字リストを設計する。初期公開の中心は汎用プリセットとし、作品専用生成機能は別段階の候補とする。
フォントの字形・約物幅・OpenType機能を維持し、文字削減と機能削除を一緒に行わない。

## 現在の実装との照合

- [`scripts/build_fonts.py`](../scripts/build_fonts.py)の`merged_font()`は元フォントのcmapを保ち、約物と縦書き代替字形を置換する。
  `palt/halt/vpal/vhal`による置換約物の二重詰めを抑止している。
- 現在の出力は`packages/merged/<family>/{ttf,otf}/Merged<family>-<Style>.<ext>`。
  `full`/`subset`区分も文字セット指定もない。
- `--merged-format`は`native/both/ttf/otf`。JP/RPの元形式はTTF、MPはOTF。
  公開用ビルドではTTF・OTFの両方を生成する。
- キャッシュは`build/fonts`で形式別にハッシュを検査する。入力はソース・輪郭・元フォント・生成コード・`uv.lock`。
- [`scripts/build_zip.py`](../scripts/build_zip.py)は6ファミリー46スタイルのcore/mergedを列挙し、計184フォントを1つのZIPに収録する。
  既存ZIPの実測は[v5比較資料](v4.1.1-to-v5.0.0.md#ダウンロード版zip)参照。
- [`scripts/test_build_fonts.py`](../scripts/test_build_fonts.py)に全文字版のcmap維持、整形、約物幅、縦書き、形式変換、キャッシュの検証がある。
  サブセット版には別の収録文字検査が必要。
- [`scripts/zip/README.md`](../scripts/zip/README.md)で、既存の末尾`s`は「カッコだけ半角化」と説明している。
  サブセットの略として`s`を再利用すると意味が衝突する。

### 全文字版の基準値（今回の実測）

対象：現作業ツリーの`packages/merged`、Regularのみ。Python 3.12.11、FontTools 4.67.0。
バイト数は未圧縮のファイルサイズ。文字数は`getBestCmap()`のコードポイント数、グリフ数とは異なる。

| ファミリー | 文字数 | グリフ数 | TTF（B） | OTF（B） |
| --- | ---: | ---: | ---: | ---: |
| YakuHanJP | 16,732 | 17,808 | 5,732,988 | 4,020,296 |
| YakuHanJPs | 16,732 | 17,808 | 5,732,516 | 4,020,316 |
| YakuHanMP | 16,689 | 17,776 | 7,460,240 | 6,170,844 |
| YakuHanMPs | 16,689 | 17,776 | 7,459,416 | 6,169,688 |
| YakuHanRP | 8,201 | 8,532 | 3,397,824 | 2,081,456 |
| YakuHanRPs | 8,201 | 8,532 | 3,397,820 | 2,079,492 |

- Regularの6ファミリー共通部分は6,506コードポイント、和集合は18,399。漢字だけの数ではない。
  全ウェイト間の一致は今回未検証。
- TTFのcmap format 14も確認。JPは17セレクター・14,787組、MPは17・14,770組、RPは7・279組のUVSがある。
  これは異体字シーケンスのエントリー数で、独立した文字数や追加グリフ数ではない。
- スポット検査では`劍`はRP/RPsの全文字版にもない。`⚔`（U+2694）・`�`（U+FFFD）も全6ファミリーにない。
  文字セットへ列挙しても元フォントにない字形は増えない。元からない文字と、サブセットで落とす文字を区別する。
- 元フォント由来の収録差を黙って共通部分へ切り詰める案は非推奨。まず希望文字セットを定義し、
  ファミリー別の不足を一覧化してから「全書体共通を保証」か「書体別の差を明示」かを決める。

再測定はリポジトリルートで以下を実行できる（既存`.venv`を使用、フォントは変更しない）。

```sh
.venv/bin/python - <<'PY'
from pathlib import Path
from fontTools.ttLib import TTFont
sets = []
for family in ('YakuHanJP', 'YakuHanJPs', 'YakuHanMP', 'YakuHanMPs', 'YakuHanRP', 'YakuHanRPs'):
    for ext in ('ttf', 'otf'):
        p = Path(f'packages/merged/{family}/{ext}/Merged{family}-Regular.{ext}')
        with TTFont(p) as f:
            cmap = set(f.getBestCmap())
            print(family, ext, p.stat().st_size, len(cmap), len(f.getGlyphOrder()))
            if ext == 'ttf':
                sets.append(cmap)
print('intersection', len(set.intersection(*sets)), 'union', len(set.union(*sets)))
PY
```

`full`移動後はパスの変更が必要。今回の計測は容量削減率・プリセットのカバー率を測ったものではない。

### TUBELEX

[公式リポジトリ](https://github.com/naist-nlp/tubelex)は日本語の語頻度、動画・チャンネル出現数、カテゴリ別頻度を公開する。
通常版は小文字化・NFKC済みで、未正規化版もある。元コーパス全文は公開しないと説明されている。
文字選定には未正規化の表層形を優先し、`Σ 語の頻度×語中の当該文字数`を補助値にする案。
ただし分かち書き・フィルタ・記号除去の影響があるため、生テキストの文字カバー率とは呼ばない。
語ごとの動画・チャンネル数を足しても、文字のユニークな文書出現数にはならない。

[リポジトリのLICENSE](https://github.com/naist-nlp/tubelex/blob/main/LICENSE)はBSD-3-Clause。
採用時は対象の頻度ファイルにもその条件が適用されるかと、取得版・帰属表示を確認する。

Wikipediaは固有名詞・専門語の補助評価候補。字幕資料は会話の比較候補。いずれも収集時期・重複・表記処理・利用条件を

## 文字セットの組み立て方（提案）

### 基礎文字と用途の追加

頻度が低くても必要な文字は、漢字順位とは独立した明示リストで扱う。

| 層 | 候補 | 判断方法 |
| --- | --- | --- |
| 基礎 | ASCIIの可視文字・空白、ひらがな・カタカナ、小書き、長音、繰り返し記号、濁点・半濁点、日本語約物 | Unicodeブロック丸ごとではなく、コードポイントと採用理由を記録 |
| 幅・表記違い | 全角英数字、半角カナ、全角空白、NBSP、円・バックスラッシュ、波ダッシュ・全角チルダ、ハイフン・マイナス類 | 実際に渡される文字列で検証。見た目が近くても別コードを同一扱いしない |
| UI・数値 | 矢印、丸数字、星・ハート・音符、単位、通貨、数学記号 | 手動候補＋UI資料で選定。絵文字やボタン図像の全面収録を目標にしない |
| 頻出漢字 | 書き言葉と口語の順位を併用 | 総頻度だけでなくレジスター別の取りこぼしを見る |
| 用途補助 | 例：龍・竜・剣・魔・闇・絆、人名・地名の表記違い | 例示段階。特定ジャンルに偏った追加を無制限に行わず、根拠を記録 |
| シーケンス | 結合濁点・半濁点、選択対象の漢字と元フォントにあるUVS | 単独コードの包含と実際の整形を別々に検証 |

coreで変更する約物は各ファミリーで全て残す案を優先する。`s`版も文字集合は通常版と揃え、半角化範囲だけを変える。
制御文字・改行・タブ・ZWJ・VSなどは、可視グリフの不足と同じ欠字判定にしない。
`.notdef`は保持するが、U+FFFDの収録とは別。元にないU+FFFDを保証文字にしない。

### 頻度の統合と段階数

- 資料ごとの文字頻度を同じ分母に正規化し、レジスターごとの順位・カバー率を併記する。
  コーパス規模が大きいだけで他資料を圧倒する生カウントの合算は避ける。
- 最初は「BCCWJのみ」「口語補助のみ」「両方の組合せ」を比較する。語頻度由来の補助値は混同せず別列に置く。
  重みは測定前に仮置きし、感度分析で順位の変化を見る。現時点で重みは未定。
- 漢字上位2,000 / 3,000 / 4,500を探索点にする案。これは漢字数であり、総文字数・公開製品名・推奨上限ではない。
  基礎文字等を加えるため、総収録数は増える。元フォント対応の検査前に「全書体で4,500漢字」と約束しない。
- 比較用の仮IDは`compact / standard / extended`。各候補は前段階の全文字を含む累積型とする。
  分割された差分フォントを重ねる方式は、組み込み時のフォールバック負担があるため初期案では採らない。
- まず1〜2段階で公開できるか判断し、容量に対する欠字減少の効果が小さい候補は公開しない。
  常用漢字全収録案・JIS第一水準案も同条件で比較し、頻度方式の改善があるか確認する。

### 正規化と再現性

[Unicode UAX #15](https://www.unicode.org/reports/tr15/)に示されるNFKCは互換上の区別を畳む。
全角・半角、丸数字、互換漢字を集計時に消すと、入力文字列で必要なコードポイントを見落とす。
元の表記を保管し、正規化した集計軸と出荷するコードポイント集合を分ける。NFCでも一部の互換漢字等が変化するので、
人名を含む入力を無条件に正規化しない。原文、NFC/NFDのかな、半角濁点などを評価に含める。

文字セットには版番号を付け、ソート済みコードポイント、文字一覧、採用理由（基礎・頻度・追加）、
資料のURL・版・取得日・SHA-256・正規化設定・生成ツール版を保存する。通常ビルドでネットから最新版を再集計しない。
固定版のリストから再生成できるようにし、更新時は追加・削除文字を公開する。
同じセット版で収録文字を黙って削らず、順位変動だけを理由に毎回入れ替えない。

## ゲーム・アプリでの評価

| 用途 | 選び方の案 | 注意点 |
| --- | --- | --- |
| 文言が固定のUI・作品台詞 | プリセット＋作品文字の追加、将来は作品専用生成 | セリフだけでなく実績・DLC・エラー・サーバー文言・権利表記も検査 |
| 更新されるテキスト | 広めのプリセット＋更新時の欠字検査 | テキスト更新とフォント更新を同時管理 |
| ユーザー名・チャット・人名 | 全文字版や適切なフォールバックも検討 | 頻度プリセットだけで任意入力を保証しない。全文字版も全Unicodeを含む意味ではない |
| 多言語UI | 日本語セットと対象言語の必要文字を別途評価 | 日本語の頻出漢字で中国語・韓国語対応を代用しない |

[Unity 6.3のFont assets説明](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-font-asset/uie-font-asset)は
Static/Dynamic/Dynamic OSを区別し、Dynamicは元フォントを含むと説明する。
一方、[同版のsubsetting説明](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-font-asset/uie-font-subsetting)は
Advanced Text Generatorでは元フォントが必要でStaticが使えないとする。
実装方式・Unityバージョン・TMP/UI Toolkitを固定せずに「静的アトラスなら元フォント不要」と一般化しない。

[Godotの説明](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html#font-prerendering)では、
事前描画対象の指定と実行時のグリフ生成が分かれている。事前描画を減らすことと、元フォントから文字を削ることは別。
この違いから、配布時はフォントに加えて、エンジンへ渡せるUTF-8文字リスト・Unicode一覧を付ける案を推奨する。

検証対象はまずUnityとGodot、アプリ向けの代表環境を選び、OS・バージョン・文字サイズ・描画方式を記録する。
今回、実エンジン・実機でのインポートや描画測定はしていない。

### 比較で必要な指標

- TTF/OTF単体のB数・圧縮後の配布サイズ・文字数・グリフ数・生成時間。
- 同じ文言・ウェイト・サイズ・padding・描画方式でのアトラス枚数/容量、ビルド容量、初回表示時間、CPU/GPUメモリ。
  同じ文字だけを描画する場合、元フォントのサブセット化でアトラスが必ず小さくなるとは限らない。
- 出現回数で重み付けした文字カバー率、漢字だけのカバー率、異なり文字カバー率、欠字のない文字列の割合。
  `文字カバー率 = 収録文字の出現回数合計 / 評価対象文字の出現回数合計`とし、制御文字等の除外条件も明記する。
- 元フォントで表示可能な評価文字だけを分母にした削減影響と、原文全体に対するカバー率を両方示す。
- `.notdef`、異体字の意図しない既定字形化、結合濁点の分離、フォールバック回数と行高・幅の変化。
  見た目が出ても別字形に置換されていれば成功扱いしない。
- 各レジスター・ジャンル・作品別の結果。平均99.9%などの単一値で未知の作品の表示保証をしない。
  例として文字ごとに独立な99.9%を仮定しても、100文字全てが揃う確率は約90.5%になる（説明用の仮定で、実測ではない）。

選定に使っていない作品を評価に用い、ゲーム・UI・人名・地名を別群にする。
採用する文字数やカバー率の合格値は、比較表を作ってから決める。

## 生成仕様と配布構成（未確定案）

### 生成順序

1. 現行処理で全文字のmergedを作る。
2. 別コピーに固定文字リストを適用し、FontTools subsetで依存字形を閉包する。
3. 必要形式へ変換し、名前・整形・収録文字を検査して保存する。

これなら約物置換のロジックを共有できる。既存の両形式出力をそれぞれ削減する案とも比較し、
「マージ→削減→変換」と「マージ→変換→削減」の時間・字形差・CFF共通化への影響を測ってから実装順序を確定する。
未保存の共有オブジェクトを直接削減してfullを壊さないよう、処理対象を分離する。

[FontTools subsetの仕様](https://fonttools.readthedocs.io/en/latest/subset/index.html)では、保持するlayout機能の指定と、
それで参照される字形の追加がある。初期案は全機能保持（`layout_features=['*']`）とlayout closure有効、
hintingも保持。縦書き・代替字形を落とす既定設定任せにはしない。
`aalt`や地域字形も残すと期待より容量が減らない可能性は実測で判断する。
UVSは基底文字と選択子の扱い、format 14の対応組を明示的に検査する。
GSUB/GPOS/GDEF、縦メトリクス、名前、著作権・ライセンス情報の保持も確認する。
「不要に見えるテーブルを全部削る最小版」は初期対象にしない。

ファイル名だけでなくname ID 1/2/3/4/6/16/17、CFF内部名をfull・各セットで区別し、
Regular/Bold等のスタイルリンクを維持する。PostScript名の文字・長さ制約も検証する。
同じ内部名のfullとsubsetがOS・エンジンで衝突しないことを確認する。

### 配布量と互換性

- TTF/OTFの両方を初期候補とし、元形式を組み込み時の第一候補として案内する。
  全46スタイル×2形式なら1セットで92フォント、3セットでは追加276フォントとなる。
  検証・ZIP容量・利用者の選択負担を踏まえ、セット数と全ウェイト提供の必要性を確認する。
- GitHub Releasesでfullとsubsetを選べるZIPに分ける案と、現在の1 ZIPに同梱する案を比較する。
  ファイル数・圧縮サイズを測る前に既存ZIPへ全候補を追加しない。
- 文字リスト、セット版・選定方針、ファミリー別の不足、ライセンスを同梱する。
- `merged/full`への移動は既存パスを変える。生成・キャッシュ・ZIP列挙・テスト・Playground等の参照を検索して移行する。
  旧パスに残ったバイナリを二重配布しないよう、削除対象を列挙して移行する。
- 実装時にルートREADME・ZIP README・v5比較資料を同時更新する。現段階では利用手順は変わっていない。

## ライセンスと参考実装

フォント側はリポジトリの`resource/*/OFL.txt`と[OFL公式FAQ](https://openfontlicense.org/ofl-faq/)を基準にする。
文字削減も改変版に当たる。フォントの著作権・OFL・Reserved Font Nameの条件を維持し、
ゲーム・アプリへ渡す際も必要なライセンス情報を同梱できる案内を用意する。
フォントのOFL、生成コードのMIT、選定資料の利用条件は別々に確認する。
頻度表を同梱するか、派生文字リストだけを同梱するかも、資料の条件を確定してから決める。

[ixkaitoのREADME](https://github.com/ixkaito/NotoSansJP-subset/blob/master/README.md)では、機能を保持する`subset`と
情報を削る`subset-min`を区別し、文字一覧と容量比較を公開している。
文字一覧の公開・容量比較という方法は参考になるが、古い元フォントの容量比や第一水準中心の文字選択は引き継がない。
同資料のWOFF系出力も今回の対象外。文字一覧の流用はしていない。
