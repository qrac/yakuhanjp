公開する段階数は容量・欠字の実測後に決める。最初から多数のバリエーションを配布しない。
続行調査ではTUBELEXを暫定採用し、BCCWJ文字表は非営利条件のため採用を保留した。

これは追加枠の提案であり、承認済みの文字セットや公開仕様ではない。元の6候補と順位は変更していない。

汎用プリセットだけでは固有名詞や作品独自の語彙を保証できないため、将来の作品テキスト追加・欠字検査にも使える
機械可読の文字リストを設計する。初期公開の中心は汎用プリセットとし、作品専用生成機能は別段階の候補とする。
フォントの字形・約物幅・OpenType機能を維持し、文字削減と機能削除を一緒に行わない。

### 決定：候補にあるが元フォントにない文字の扱い

2026-10-21ユーザー指定。大元の文字選定は維持し、元フォントにない候補文字は、そのフォントの生成から省いて記録する。

- 共通候補集合を`S`、対象フォントのcmapにある文字集合を`F`として、実収録文字は`S ∩ F`、省略文字は`S − F`とする。
- 一つの書体にないことを理由に、共通候補や他書体の生成対象からその文字を除かない。
- 省いた分を下位順位の文字で補充せず、別書体の字形も移植しない。同じ候補IDでも実収録数は書体ごとに異なり得る。
- 省略記録には候補ID・元フォントの識別情報・ファミリー/スタイル・文字・コードポイント・件数・理由（元フォント未収録）を含める。
  内容が同じスタイルはまとめてよい。TTF/OTFで収録範囲が異なる場合は形式別にも記録する。
- 候補の目標文字数/カバー率と、実際に生成したフォントの収録数/カバー率を区別して表示する。
- この省略は生成エラーにしない。一方、元フォントにある選択文字が生成過程で落ちた場合は検証エラーにする。

現在の調査スクリプトは既にこの方式で試作しており、`report.json`の`missing_by_family`に省略文字のコードポイントと
対象スタイル、`regular_support`に基礎文字/漢字別の省略一覧と実カバー率を保存している。
候補IDは各結果のキー、元フォントのハッシュは`font_inventory`に記録し、文字はコードポイントから復元できる。
配布用ビルドへ実装するときは、人が読める文字・件数・理由も明示した省略一覧を添える。

### 低頻度文字の除外候補リスト（検討方針）

2026-10-21ユーザー提案。日本語で極めて使用頻度が低い文字について、subset向けの除外候補リストを別途設ける。
この段階では文字の自動削除を承認したものではなく、具体的な除外文字・頻度の閾値は未確定。

- 元の頻度順位・基礎文字・人名追加枠の選定根拠は維持し、除外の判断を別リストで追跡する。
  上位3,000に入らず初めから選ばれない漢字と、選定済み候補から意図的に除く文字を区別する。
- 調査対象は、用途上不要な可能性のある古い表記・互換記号・特殊な文字など。分類だけで一括除外せず、
  各文字の実際の利用と用途を確認する。候補リスト外の文字を列挙するだけでは現在の試作容量は減らない。
- TUBELEXの不出現だけで除外しない。語彙表での記号の欠落・資料の偏りがあるため、
  頻度値は資料/版・文字種・対象ジャンルとともに記録し、人名・UI・別資料で必要性を確認する。
- 基本のかな・coreの対象約物・採用する人名文字など、用途上残すと決めた文字は保持指定を優先する。
  一般文章では低頻度でも人名に必要な漢字・異体字は、低頻度という理由だけで除かない。
- リストの項目は文字・コードポイント・除外理由・資料別頻度/出典・影響する用途・状態（候補/除外/維持）・判断日。
  保持指定との衝突も記録し、未判断の候補をそのまま生成へ適用しない。
- 将来の生成は、共通の原候補から承認済み除外文字を引いた有効候補を作り、その後に各元フォントとの積集合を取る。
  「選定上の除外」と「有効候補にはあるが元フォント未収録のため省略」を別の理由・一覧として出力する。
  前者は共通の選定判断、後者はフォントごとの収録差であり、既存の省略方針を変更しない。
- 除外前後で容量、文字/文字列カバー率、人名・UIサンプル、縦書き・UVSの挙動を比較する。
  コードポイントを減らしても共有グリフやOpenType依存字形が残る場合があるため、削減効果は字数から推定せず実測する。

次の選定作業では、人名追加枠と保持指定を整理したうえで除外候補を抽出する。fullの文字集合はこの除外リストの対象外。
除外リスト・適用処理は未実装で、既存の候補リストや試作フォントから文字は削っていない。

対象：現作業ツリーの`packages/merged`、Regularのみ。Python 3.12.11、FontTools 4.67.0。
バイト数は未圧縮のファイルサイズ。文字数は`getBestCmap()`のコードポイント数、グリフ数とは異なる。

| YakuHanJPs | 16,732 | 17,808 | 5,732,516 | 4,020,316 |

- Regularの6ファミリー共通部分は6,506コードポイント、和集合は18,399。漢字だけの数ではない。
  続行調査で、各ファミリー内の全ウェイトのcmapが一致することも確認済み。

  文字セットへ列挙しても元フォントにない字形は増えない。元からない文字と、サブセットで落とす文字を区別する。
- 共通候補は書体間の共通部分へ切り詰めない。2026-10-21決定により、元フォントにない文字は書体別に省略し、その差を記録する。

再測定はリポジトリルートで以下を実行できる（既存`.venv`を使用、フォントは変更しない）。

```sh
.venv/bin/python - <<'PY'
from pathlib import Path
from fontTools.ttLib import TTFont
sets = []
for family in ('YakuHanJP', 'YakuHanJPs', 'YakuHanMP', 'YakuHanMPs', 'YakuHanRP', 'YakuHanRPs'):
    for ext in ('ttf', 'otf'):
        p = Path(f'packages/merged/{family}/{ext}/Merged{family}-Regular.{ext}')
        with TTFont(p) as f:
            cmap = set(f.getBestCmap())
            print(family, ext, p.stat().st_size, len(cmap), len(f.getGlyphOrder()))
            if ext == 'ttf':
                sets.append(cmap)
print('intersection', len(set.intersection(*sets)), 'union', len(set.union(*sets)))
PY
```

### TUBELEX

[公式リポジトリ](https://github.com/naist-nlp/tubelex)は日本語の語頻度、動画・チャンネル出現数、カテゴリ別頻度を公開する。
通常版は小文字化・NFKC済みで、未正規化版もある。元コーパス全文は公開しないと説明されている。
文字選定には未正規化の表層形を優先し、`Σ 語の頻度×語中の当該文字数`を補助値にする案。
ただし分かち書き・フィルタ・記号除去の影響があるため、生テキストの文字カバー率とは呼ばない。
語ごとの動画・チャンネル数を足しても、文字のユニークな文書出現数にはならない。

[リポジトリのLICENSE](https://github.com/naist-nlp/tubelex/blob/main/LICENSE)はBSD-3-Clause。
採用時は対象の頻度ファイルにもその条件が適用されるかと、取得版・帰属表示を確認する。

### その他の候補の優先度

Wikipediaは固有名詞・専門語の補助評価候補。字幕資料は会話の比較候補。いずれも収集時期・重複・表記処理・利用条件を
確認してから追加する。NWJCのようなWebコーパスも将来の補助候補だが、今回は一次候補の確認を優先した。
検索で見つかる出所不明の漢字順位表は採用せず、資料数を増やすより再現可能な基準を先に作る。

## 文字セットの組み立て方（提案）

### 基礎文字と用途の追加

頻度が低くても必要な文字は、漢字順位とは独立した明示リストで扱う。

| 層 | 候補 | 判断方法 |
| --- | --- | --- |
| 基礎 | ASCIIの可視文字・空白、ひらがな・カタカナ、小書き、長音、繰り返し記号、濁点・半濁点、日本語約物 | Unicodeブロック丸ごとではなく、コードポイントと採用理由を記録 |
| 幅・表記違い | 全角英数字、半角カナ、全角空白、NBSP、円・バックスラッシュ、波ダッシュ・全角チルダ、ハイフン・マイナス類 | 実際に渡される文字列で検証。見た目が近くても別コードを同一扱いしない |
| UI・数値 | 矢印、丸数字、星・ハート・音符、単位、通貨、数学記号 | 手動候補＋UI資料で選定。絵文字やボタン図像の全面収録を目標にしない |
| 頻出漢字 | 書き言葉と口語の順位を併用 | 総頻度だけでなくレジスター別の取りこぼしを見る |
| 用途補助 | 例：龍・竜・剣・魔・闇・絆、人名・地名の表記違い | 例示段階。特定ジャンルに偏った追加を無制限に行わず、根拠を記録 |
| シーケンス | 結合濁点・半濁点、選択対象の漢字と元フォントにあるUVS | 単独コードの包含と実際の整形を別々に検証 |

coreで変更する約物は各ファミリーで全て残す案を優先する。`s`版も文字集合は通常版と揃え、半角化範囲だけを変える。
制御文字・改行・タブ・ZWJ・VSなどは、可視グリフの不足と同じ欠字判定にしない。
`.notdef`は保持するが、U+FFFDの収録とは別。元にないU+FFFDを保証文字にしない。

### 頻度の統合と段階数

- 資料ごとの文字頻度を同じ分母に正規化し、レジスターごとの順位・カバー率を併記する。
  コーパス規模が大きいだけで他資料を圧倒する生カウントの合算は避ける。
- 最初は「BCCWJのみ」「口語補助のみ」「両方の組合せ」を比較する。語頻度由来の補助値は混同せず別列に置く。
  重みは測定前に仮置きし、感度分析で順位の変化を見る。現時点で重みは未定。
- 漢字上位2,000 / 3,000 / 4,500を探索点にする案。これは漢字数であり、総文字数・公開製品名・推奨上限ではない。
  基礎文字等を加えるため、総収録数は増える。元フォント対応の検査前に「全書体で4,500漢字」と約束しない。
- 比較用の仮IDは`compact / standard / extended`。各候補は前段階の全文字を含む累積型とする。
  分割された差分フォントを重ねる方式は、組み込み時のフォールバック負担があるため初期案では採らない。
- まず1〜2段階で公開できるか判断し、容量に対する欠字減少の効果が小さい候補は公開しない。
  常用漢字全収録案・JIS第一水準案も同条件で比較し、頻度方式の改善があるか確認する。

### 正規化と再現性

[Unicode UAX #15](https://www.unicode.org/reports/tr15/)に示されるNFKCは互換上の区別を畳む。
全角・半角、丸数字、互換漢字を集計時に消すと、入力文字列で必要なコードポイントを見落とす。
元の表記を保管し、正規化した集計軸と出荷するコードポイント集合を分ける。NFCでも一部の互換漢字等が変化するので、
人名を含む入力を無条件に正規化しない。原文、NFC/NFDのかな、半角濁点などを評価に含める。

文字セットには版番号を付け、ソート済みコードポイント、文字一覧、採用理由（基礎・頻度・追加）、
資料のURL・版・取得日・SHA-256・正規化設定・生成ツール版を保存する。通常ビルドでネットから最新版を再集計しない。
固定版のリストから再生成できるようにし、更新時は追加・削除文字を公開する。
同じセット版で収録文字を黙って削らず、順位変動だけを理由に毎回入れ替えない。

## ゲーム・アプリでの評価

| 用途 | 選び方の案 | 注意点 |
| --- | --- | --- |
| 文言が固定のUI・作品台詞 | プリセット＋作品文字の追加、将来は作品専用生成 | セリフだけでなく実績・DLC・エラー・サーバー文言・権利表記も検査 |
| 更新されるテキスト | 広めのプリセット＋更新時の欠字検査 | テキスト更新とフォント更新を同時管理 |
| ユーザー名・チャット・人名 | 全文字版や適切なフォールバックも検討 | 頻度プリセットだけで任意入力を保証しない。全文字版も全Unicodeを含む意味ではない |
| 多言語UI | 日本語セットと対象言語の必要文字を別途評価 | 日本語の頻出漢字で中国語・韓国語対応を代用しない |

[Unity 6.3のFont assets説明](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-font-asset/uie-font-asset)は
Static/Dynamic/Dynamic OSを区別し、Dynamicは元フォントを含むと説明する。
一方、[同版のsubsetting説明](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-font-asset/uie-font-subsetting)は
Advanced Text Generatorでは元フォントが必要でStaticが使えないとする。
実装方式・Unityバージョン・TMP/UI Toolkitを固定せずに「静的アトラスなら元フォント不要」と一般化しない。

[Godotの説明](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html#font-prerendering)では、
事前描画対象の指定と実行時のグリフ生成が分かれている。事前描画を減らすことと、元フォントから文字を削ることは別。
この違いから、配布時はフォントに加えて、エンジンへ渡せるUTF-8文字リスト・Unicode一覧を付ける案を推奨する。

検証対象はまずUnityとGodot、アプリ向けの代表環境を選び、OS・バージョン・文字サイズ・描画方式を記録する。
今回、実エンジン・実機でのインポートや描画測定はしていない。

### 比較で必要な指標

- TTF/OTF単体のB数・圧縮後の配布サイズ・文字数・グリフ数・生成時間。
- 同じ文言・ウェイト・サイズ・padding・描画方式でのアトラス枚数/容量、ビルド容量、初回表示時間、CPU/GPUメモリ。
  同じ文字だけを描画する場合、元フォントのサブセット化でアトラスが必ず小さくなるとは限らない。
- 出現回数で重み付けした文字カバー率、漢字だけのカバー率、異なり文字カバー率、欠字のない文字列の割合。
  `文字カバー率 = 収録文字の出現回数合計 / 評価対象文字の出現回数合計`とし、制御文字等の除外条件も明記する。
- 元フォントで表示可能な評価文字だけを分母にした削減影響と、原文全体に対するカバー率を両方示す。
- `.notdef`、異体字の意図しない既定字形化、結合濁点の分離、フォールバック回数と行高・幅の変化。
  見た目が出ても別字形に置換されていれば成功扱いしない。
- 各レジスター・ジャンル・作品別の結果。平均99.9%などの単一値で未知の作品の表示保証をしない。
  例として文字ごとに独立な99.9%を仮定しても、100文字全てが揃う確率は約90.5%になる（説明用の仮定で、実測ではない）。

選定に使っていない作品を評価に用い、ゲーム・UI・人名・地名を別群にする。
採用する文字数やカバー率の合格値は、比較表を作ってから決める。

## 生成仕様と配布構成（未確定案）

### 生成順序

1. 現行処理で全文字のmergedを作る。
2. 別コピーに固定文字リストを適用し、FontTools subsetで依存字形を閉包する。
3. 必要形式へ変換し、名前・整形・収録文字を検査して保存する。

これなら約物置換のロジックを共有できる。既存の両形式出力をそれぞれ削減する案とも比較し、
「マージ→削減→変換」と「マージ→変換→削減」の時間・字形差・CFF共通化への影響を測ってから実装順序を確定する。
未保存の共有オブジェクトを直接削減してfullを壊さないよう、処理対象を分離する。

[FontTools subsetの仕様](https://fonttools.readthedocs.io/en/latest/subset/index.html)では、保持するlayout機能の指定と、
それで参照される字形の追加がある。初期案は全機能保持（`layout_features=['*']`）とlayout closure有効、
hintingも保持。縦書き・代替字形を落とす既定設定任せにはしない。
`aalt`や地域字形も残すと期待より容量が減らない可能性は実測で判断する。
UVSは基底文字と選択子の扱い、format 14の対応組を明示的に検査する。
GSUB/GPOS/GDEF、縦メトリクス、名前、著作権・ライセンス情報の保持も確認する。
「不要に見えるテーブルを全部削る最小版」は初期対象にしない。

### 配置と名前

```text
packages/merged/
├── full/<family>/{ttf,otf}/...
└── subset/<family>/{ttf,otf}/...
```

上記は候補。`build/fonts`とZIP内でも同じ区分を使う案。
全文字版のファイル名は維持し、サブセット版だけ名前を変える案を優先するが、まだ決定しない。

| ファイル名候補 | 利点 | 注意 |
| --- | --- | --- |
| `MergedYakuHanJPSubset-Regular.ttf` | 元ファミリー名に区分を追記し、styleを末尾に維持 | 現時点の推奨案 |
| `MergedSubsetYakuHanJP-Regular.ttf` | styleが末尾の現構造を維持しやすい | 接頭辞が長くなる |
| `MergedYakuHanJP-Regular-subset.ttf` | 既存名への追記が分かりやすい | style末尾という現構造は崩れる |

ファイル名だけでなくname ID 1/2/3/4/6/16/17、CFF内部名をfull・各セットで区別し、
Regular/Bold等のスタイルリンクを維持する。PostScript名の文字・長さ制約も検証する。
同じ内部名のfullとsubsetがOS・エンジンで衝突しないことを確認する。

### 配布量と互換性

- TTF/OTFの両方を初期候補とし、元形式を組み込み時の第一候補として案内する。

### 元フォント側の不足と基礎文字の調整

| 全体順位の漢字数 | JPの漢字不足 | MPの漢字不足 | RPの漢字不足 |
| --- | ---: | ---: | ---: |
| 2,000 | 0 | 0 | 0 |
| 3,000 | 0 | 0 | 14 |
| 4,500 | 23 | 23 | 488 |

全46スタイルのcmapを調べ、同一ファミリーの全ウェイトが同じ集合であることを確認した。
通常版と`s`版の各対も同じ集合だった。
RPの3,000字候補で足りない漢字は`宦寨慥攪攫笘箴繩聟蔡蜷鍮顏髯`。
不足を反映すると、この資料内でのRPの漢字カバー率は全体99.9110%、gaming 99.9463%、news 99.9309%。
2026-10-21決定により、この14字は共通候補に残したままRP/RPsの生成から省く。別文字での補充は行わない。
例えば「3,000漢字候補」のRPは実収録2,986漢字となり、候補漢字3,000字と省略14字を併記する。

基礎602文字にも元フォントとの差がある。JP/MPにない`⇑⇓✔✕✖`、MPにもない`㋿`なども、
候補に残したまま、その文字を持たない書体の生成から省いて記録する。RPには一部の互換単位記号と、他書体由来の縦書き互換コードがない。
coreソースの和集合を取ったことで、RPに元々ないJP/MP用の縦書きコードも候補に入っている。
これはRP自身の縦書き代替グリフが失われたことを意味しない。
基礎文字・任意の追加記号・ファミリー固有の代替字形の整理は、元フォントの収録差とは別に用途上の必要性から判断する。

### 検証方法と残作業

## 別資料評価と基礎文字の補助枠案

2026-10-21実施。上記の候補6種を固定して評価し、結果を見てから補助枠案を追加した。
選定用のTUBELEXデータ・元の候補リスト・順位・初期実測は変更していない。

### 評価対象と方法

- Godotの日本語エディターUI翻訳：5,689文字列、116,612文字、879種類。
- Godotの日本語プロパティUI翻訳：1,955文字列、15,246文字、673種類。
- Ren’Py同梱サンプルゲーム「The Question」の日本語会話・地の文・選択肢等：76文字列、1,602文字、293種類。
- 固定版のファイルURL・SHA-256・ライセンスの確認根拠は[評価資料の記録](merged-subset-experiment/validation-sources.json)参照。
  Godot翻訳はファイルヘッダーでソースと同じライセンス（MIT）と明記されている。
  Ren’Py公式説明は大部分をMITとするが、選んだ日本語台本には個別条件の明記がないため、本文の再配布や文字選定への転用はしていない。
  今回はエンジン依存ライブラリ・画像・音声を取得/利用していない。
- POは翻訳済み`msgstr`だけを数え、英語原文・ヘッダー・fuzzy・obsolete・空訳を除外。
  台本はコメントの原文・`old`を除き、表示文と`new`を抽出。認識できない文構文は黙って無視せずエラーにする。
- 対応する装飾タグ・プレースホルダー・改行/タブ等の制御文字・不可視書式文字・VSを除外して数える。
  空白は数え、Unicode正規化は行わない。実行時に埋め込む変数値や未翻訳時の英語フォールバックは評価外。
- 文字列は翻訳レコード単位。表示頻度での重み付けやゲームのプレイ分岐による出現回数はない。
  異なり文字・文字出現回数・全文字を含むレコードの割合を分け、元フォントの収録範囲内だけでの包含率も記録した。

### 固定した候補6種の結果

下表は全体順位候補の結果。「文字」は出現回数の包含率、「文字列」は全文字を含むレコードの割合（%）。
ここでは元フォントによる省略を反映する前の、共通候補の結果を示す。各書体の実値は[評価結果](merged-subset-experiment/validation-report.json)参照。

| 対象 | 2,000漢字：文字 | 2,000漢字：文字列 | 3,000漢字：文字 | 3,000漢字：文字列 | 4,500漢字：文字 | 4,500漢字：文字列 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Godotエディター | 99.9811 | 99.6309 | 99.9940 | 99.8770 | 99.9940 | 99.8770 |
| Godotプロパティ | 99.9082 | 99.2839 | 100 | 100 | 100 | 100 |
| The Question | 99.9376 | 98.6842 | 100 | 100 | 100 | 100 |

2,000字候補から漏れた漢字には、Godotで`矩/遷/蔽/錐/弧/填/累`、台本で`摺`があった。
3,000字に増やすとこれらは入る。gamingを加重した3,000字候補も、この3資料では全体順位版と同じ包含率だった。
3,000字候補のGodotエディターで残る文字は`π/ε/τ/φ/响`。4,500字に増やしても結果は変わらなかった。
`响`は訳文に含まれる簡体字で、この一例を理由に日本語の漢字順位を変えない。

Godotは技術用語の多いUI、The Questionは短い翻訳サンプルであり、一般の日本語文書・商用ゲーム・固有名詞の代表性はない。
この結果は任意のゲームでの欠字ゼロを保証しない。今後は別ジャンル・人名を含む長い作品の検証が有用。

### 基礎文字の役割と追加案

[基礎文字の役割・追加案](merged-subset-experiment/base-policy-proposal.json)で、現行602文字を次の用途へ整理した。
全て「候補に要求する文字」であり、どの書体でも必ず字形があるという意味ではない。未収録なら既定方針どおり省略する。

- 基礎表記：ASCII・かな・日本語約物。
- 入力互換：全角英数字・半角カナ。
- UI表記：空白・通貨・引用符・方向/状態記号。
- 互換記号：囲み数字・単位・元号。新しい作品で不要でも、入力済みテキストへの対応枠として残す案。
- core維持：符号化済みの約物と縦書き互換文字。OpenTypeの縦書き代替字形の閉包とは別に扱う。
- 追加提案：ギリシャ文字49字と数学記号28字。ギリシャ文字は今回不足した4字だけを足すのでなく、大小文字の組で定義。
  数学記号は無限大・比較・平方根・集合等のUI用途からの提案で、頻度上位漢字へ混ぜない。

合計679文字＋上位3,000漢字＝3,679文字の[補助枠付き草案](merged-subset-experiment/general-3000-ui-math-draft.txt)を作成した。
元候補の全3,602文字を含み、追加77文字がある。フォントにないことを理由とする候補削除・補充はない。
この草案は人名追加枠を含む前のもの。以後のユーザー指定により、人名の表記違いも初回の追加枠として調査・選定する。

草案ではGodotエディターの候補包含率が99.9991%、全文字を含む文字列は99.9824%となり、残る文字は`响`だけ。
JP/MPの実フォントでは元にない`✕`も省くため、文字包含率は99.9983%、文字列は99.9648%。
RPは`响`を元から含まず99.9991% / 99.9824%。他の2資料は3書体とも100%だった。
この草案は**同じ評価資料の不足を見た後の調整案**なので、この数値を新たな独立評価の成績とはしない。

### 草案の容量と省略記録

補助枠付き草案をRegularの3書体×2形式で試作した。単位はB、括弧内は初期3,000漢字候補からの増加量。

| 書体 | TTF | OTF | 共通候補 | 実収録 | 省略 |
| --- | ---: | ---: | ---: | ---: | ---: |
| JP | 1,545,608（+18,472） | 1,119,880（+15,004） | 3,679 | 3,673 | 6 |
| MP | 2,012,268（+20,180） | 1,719,496（+17,844） | 3,679 | 3,672 | 7 |
| RP | 1,762,920（+10,112） | 1,215,380（+6,336） | 3,679 | 3,630 | 49 |

ギリシャ文字・数学記号の追加による増加は、この試作で1ファイル約6〜20KB。元にない記号は省略記録へ含めた。
JPの省略は`⇑⇓≒✔✕✖`、MPはそれに`㋿`を加えた7文字。RPの省略49文字には既出の14漢字が含まれる。

省略一覧のサンプルとして、全46スタイル×TTF/OTF＝92件ずつ、候補ID・形式・元ファイル/ハッシュ・
候補数/実収録数/省略数・省略文字/コードポイント・理由をJSON化した。
[初期3,000漢字候補](merged-subset-experiment/general-3000-omissions.json)と
[補助枠付き草案](merged-subset-experiment/general-3000-ui-math-draft-omissions.json)を参照。

草案6フォントのcmap・グリフ対応・横/縦メトリクス・行高・対象UVS全組の整形を検証し、64,064条件で全文字版と一致した。
PO/台本の抽出・装飾/変数除外・文字と文字列の評価差を確認する4テストを追加し、従来の集計テストと合わせて8件成功。
試作は`build/subset-research/ui-math-draft-fonts`内だけ。名前の衝突回避・OS/エンジンでの描画は未検証で、配布用ではない。

### 次段階に向けた推奨案

初期は「全体頻度上位3,000漢字＋基礎679文字＋人名向け追加枠」の1セットを検討する。
2,000漢字は軽量だが今回のUI/台本にも漏れがあり、4,500漢字は同資料で改善せず容量が増えた。
軽量版・拡張版・gaming加重版は今回の比較から直ちに公開せず、具体的な需要が出たら別セットとして判断する。
常用漢字・人名・別ジャンル・別の書き言葉資料の診断はまだ残り、この1セット案を最終決定したわけではない。

次はこの案を基にファイル名・内部名・セットID・ZIP構成を具体化し、公開仕様を確定してから通常ビルドへ組み込む。
`merged/full`・`merged/subset`への移動や配布用バイナリの更新はまだ行っていない。

命名・配布についての具体案（未確定）は以下。ファイル名での`subset`の位置はユーザーが未指定のため、決定事項とは分ける。

- `Standard`や`standard`の区分は付けない。文字集合の版番号をmanifestに保存し、フォント製品のリリース版と区別する。
- 全文字版は`merged/full/<family>/{ttf,otf}/Merged<family>-<Style>.<ext>`とし、ファイル名・内部名を維持する。
- サブセット版は`merged/subset/<family>/{ttf,otf}/Merged<family>Subset-<Style>.<ext>`。
  例：`MergedYakuHanJPSubset-Regular.ttf`。末尾のスタイル名を保ち、`s`は従来のカッコ限定版の意味で維持する。
- 内部のファミリー名にも`Subset`を加え、全文字版と区別する。TTF/OTFで同じスタイルの別形式という関係は維持する。
- 初期は全6ファミリー・46スタイル×2形式＝92サブセットフォントを想定し、core・全文字版と同じ
  `YakuHanJP_v<version>.zip`へ収録する。合計276フォントを想定するが、全スタイルの生成とZIP容量測定は未実施。
- ZIPには文字集合manifest・共通候補一覧・フォント別の省略一覧・README・必要なライセンスを同梱し、
  WOFF/WOFF2・CSSを含めない。ZIP容量は全スタイルを生成してから測定する。

実装時にはこの構成を生成先とキャッシュキーに反映し、旧配置の不要な生成物を列挙して移行する。
名前・パス・同梱範囲の確定、共存確認、全スタイルの生成とZIP作成は残作業。

再現は[評価スクリプト](../scripts/evaluate_merged_subset.py)を使う。
`validation-sources.json`の`local_path`へ対応する固定URLを取得してから、次を実行する（取得は別工程）。

```sh
.venv/bin/python scripts/evaluate_merged_subset.py \
  --source-root /path/to/downloaded-sources \
  --output build/subset-research/validation \
  --font-output build/subset-research/ui-math-draft-fonts
.venv/bin/python -m unittest discover -s scripts -p 'test_*merged_subset.py'
```

原文はリポジトリへ同梱せず、派生した評価値と文字一覧だけを保存している。
